# 问数与知识库：生产化改造说明

这份文档说明 2026-10-08 这一轮给「智能问数」和「企业知识库」加上的东西：批量入库、定时任务、告警、高并发保护、降级、监控、链路追踪，以及换成公司自建模型（vLLM + Qwen3）的方法。
实测数字见第 9 节；哪些验证过、哪些没验证过见第 10 节。

## 1. 总览

```
                    ┌──────────── 在线请求（同步，流式输出）────────────┐
用户 → Nginx → 入口闸门（按人限流 + 总并发上限）→ 问数 8093 / 知识库 8094
                                                     │  每个依赖一个熔断器 + 并发闸门 + 超时
                                                     ├→ 大模型（主 → 备用 → 不用模型的降级回答）
                                                     ├→ Milvus（挂了 → MySQL 全文检索）
                                                     ├→ 重排模型（忙 → 跳过重排）
                                                     ├→ ERP 数据库（只读账号，最多 8 条 SQL 同时跑）
                                                     └→ Redis（缓存、限流；挂了 → 放行）

                    ┌──────────── 离线任务（异步，走消息队列）────────────┐
共享目录 / PLM / 压缩包 → 建批次 → RabbitMQ → 消费线程 → 入库流程 → 批次汇总通知
定时任务（调度器 + Redis 锁）：EAS 同步、目录扫描、对账、健康检查、周报
告警中心：规则触发 → 去重 → 飞书机器人 + 邮件 → 确认 / 自动恢复

                    ┌──────────── 观测 ────────────┐
Prometheus 抓 /metrics → Grafana 看板和规则　　Langfuse 记录每次问答的完整链路
```

## 2. 为什么是 RabbitMQ，为什么在线问答不走队列

- 批量入库是典型的「任务队列」：一个文件一条消息，交给一个消费者处理，处理完确认，失败要重试、重试完要有地方放。RabbitMQ 原生支持确认、延迟重试和死信队列。Kafka 擅长的是海量事件流和多方订阅回放，这里用不上，运维也更重。
- 在线问答是同步的流式输出，中间塞一个队列只会更慢。在线这条路靠限流、并发闸门、缓存、超时和模型服务自身的合批来扛。

队列结构（每条消息都是持久化的，发布要确认，消费要手动确认）：

| 队列 | 用途 |
| --- | --- |
| `kb.ingest` | 工作队列，一条消息是一个文件的入库任务 |
| `kb.ingest.retry.30` / `.120` / `.600` | 延迟重试：消息在里面停留 30 秒、2 分钟、10 分钟，到期自动回到工作队列 |
| `kb.ingest.dlq` | 死信：重试用完仍失败，或者属于重试也没用的问题 |

消费者处理到一半崩溃时，没有确认的消息会被 RabbitMQ 重新投递；入库流程本身是幂等的（确定性主键 + 同版本同内容跳过），所以重复投递不会产生重复数据。

**没做的**：问数的 Excel 导出和审计日志写入目前还是同步的，没有改成走队列。

## 3. 批量入库

三种来源，都会生成一个「批次」：

| 来源 | 说明 |
| --- | --- |
| 共享目录扫描 | 目录约定是 `<共享目录>/<文档类型>/<编号>__v<版本>__<标题>.<扩展名>`，文档类型决定默认的密级和可见范围；也可以在根目录放一份 `manifest.csv` 逐个指定。只入新增和内容有变化的文件 |
| PLM 同步 | 拉 PLM 里的现行文档，同样只入有变化的 |
| 上传压缩包 | 解压后按和共享目录一样的约定识别 |

执行规则：

- 单个文件失败不影响整批。临时故障（网络、模型服务）重试 3 次；文件本身的问题（加密、损坏、类型不支持、版本冲突）不重试，直接跳过。
- 一批处理了至少 10 个文件后，失败比例超过 20% 就**自动暂停整批**并发严重告警，人工确认后可以继续或取消。
- 一批结束只发一封汇总，逐条列出失败的文件和原因。
- 消息队列连不上时，这一批自动改成进程内顺序执行并告警，功能不中断。
- 页面上可以暂停、继续、取消、重试失败项，也保留了单文件上传作为补录入口。

## 4. 定时任务

进程内调度器加 Redis 锁（多实例部署时同一时刻只有一个实例执行）。每个任务可以在页面上启停和手动触发，每次运行记一条日志；失败进告警中心，下次成功自动恢复。

| 任务 | 时间 |
| --- | --- |
| 同步金蝶 EAS 物料和 BOM | 每天 02:00 |
| 扫描共享目录增量入库 | 每天 02:30 |
| 同步 PLM 现行文档 | 每天 02:40 |
| 全库对账并清理旧版本 | 每天 03:30 |
| 重建知识图谱 | 每天 04:00 |
| 依赖健康检查和告警规则 | 每 1 分钟 |
| Bad Case 周报 | 每周一 09:00 |

## 5. 告警

规则触发后进告警中心：同一个问题只保留一条、重复触发只累加次数；一直没恢复的每 60 分钟再提醒一次；问题消失后自动关闭并发「已恢复」。

| 类别 | 规则 | 级别 |
| --- | --- | --- |
| 依赖 | MySQL、Milvus、大模型不可用 | 严重 |
| 依赖 | Redis、RabbitMQ 不可用；金蝶 EAS 数据超过 36 小时没同步 | 重要 |
| 依赖 | Neo4j 不可用 | 提示 |
| 入库 | 批次失败比例超限被自动暂停 | 严重 |
| 入库 | 批次有失败项、队列积压超过 200、任务运行超过 30 分钟、定时任务失败 | 重要 |
| 服务 | 熔断器打开、近 15 分钟 P95 超过 30 秒、拒答比例超过 50% | 重要 |
| 其他 | 邮件发送失败、共享目录有不符合约定的文件 | 提示 |

渠道：飞书自定义机器人（卡片消息，带签名校验）和邮件发件箱。本地联调时飞书指向模拟接收端，消息在 <http://localhost:8096/feishu/messages> 能看到；换成真实机器人只改 `.env` 里的 `FEISHU_WEBHOOK` 和 `FEISHU_SECRET`。

## 6. 高并发保护

| 手段 | 做法 | 默认值 |
| --- | --- | --- |
| 按人限流 | Redis 计数，一个人一分钟内的提问次数有上限，超了返回 429 和「多少秒后再试」 | 30 次 / 分钟 |
| 总并发上限 | 同时在处理的提问数有上限，超了立刻返回「人多请稍后」，不让请求堆到超时 | 知识库 8，问数 16 |
| 大模型并发闸门 | 同时打到模型服务的请求数有上限，多的排队，排不上就走降级 | 16 路 |
| 重排并发闸门 | 重排一次只跑一个，最多 4 个排队，等超过 10 秒就不排了 | — |
| 数据库并发闸门 | 问数同时最多 8 条分析 SQL，保护业务库 | 8 条 |
| 超时 | 向量检索 8 秒，生成回答 90 秒，单次模型调用 60 秒，SQL 执行有最长时间 | — |
| 缓存 | 问题向量（1 天）、完整回答（10 分钟，按问题 + 角色 + 知识库版本）；问数原有的路由、结果、回答三层缓存保留。知识库内容一变，版本号加一，旧缓存自动失效 | — |

要说清楚的一点：这些手段解决的是「过载时不垮、能给出明确反馈」，不能凭空提高吞吐。吞吐的上限由模型服务决定，要靠第 8 节的 GPU 部署来提高。

## 7. 降级

每个依赖配一个熔断器：连续失败几次就「断开」30 秒，期间不再去碰它、直接走降级；到时间放一个请求试探，成功就恢复。

| 出问题的环节 | 知识库 | 问数 |
| --- | --- | --- |
| 大模型 | 先切备用模型；没有备用或也不可用 → 返回检索到的原文摘录，不编答案 | 先切备用模型。都不可用时：制度问题照常检索并直接给原文；10 分钟内问过的数据问题靠路由缓存照常查数（没有文字解读）；全新的数据问题需要模型来理解，如实告知；写操作照样被规则拦住 |
| Milvus | 改用 MySQL 全文检索，权限和版本规则不变 | 制度问答受影响，数据问答不受影响 |
| 重排 | 跳过重排，用融合后的前 5 条 | — |
| ERP 数据库 | — | 排队；连续失败则熔断，给出能看懂的提示 |
| Neo4j | 跳过图谱 | — |
| Redis | 限流和缓存暂时失效，问答照常 | 同左 |
| RabbitMQ | 批量入库改成进程内执行 | — |
| 金蝶 EAS | 继续用本地镜像，超过 36 小时告警 | — |

每一次降级都会在回答上方明确标出来（例如「已降级：当前提问的人多，本次没有做精排」），同时记指标、记链路；熔断器打开超过 1 分钟触发告警。

## 8. 监控、链路追踪、自建模型

| 工具 | 管什么 | 地址（本机） |
| --- | --- | --- |
| Prometheus | 每 15 秒抓两个服务和 RabbitMQ 的指标，评估告警规则 | <http://localhost:9091> |
| Grafana | 看板「问数与知识库 运行监控」：请求量、P50 / P95、首字延迟、各步骤耗时、降级和拒绝次数、熔断器、资源池、缓存命中率、token、队列 | <http://localhost:3003> |
| Langfuse | 每次问答一条链路：每一步的输入输出、检索到的资料和分数、提示词和回答、token、耗时、降级点、用户反馈 | <http://localhost:3002>（可选启动） |
| RabbitMQ 管理页 | 队列长度、消费速率 | <http://localhost:15673> |

分工：**Prometheus 和 Grafana 看整体健康并触发告警；Langfuse 看单次请求、给开发排查用。降级是代码里的熔断器做的，Langfuse 只负责把「在哪一步降级了、为什么」记下来。**
问答页面上，管理员能看到每条回答的「查看链路」入口；Bad Case 池里每条记录也带链路地址。

Langfuse 用的是 2.x 单容器版本（只依赖一个 PostgreSQL），适合本地和小规模；数据量大了以后应换成 3.x（需要 ClickHouse）。启动方式：

```bash
cd assistant && docker compose --profile langfuse up -d
```

**换成 vLLM + Qwen3**：模型地址、模型名、是否关闭思考模式、备用模型都是配置项，代码不用改；向量和重排模型可以拆成独立服务放到 GPU 上。详细步骤和注意事项见 `assistant/deploy/vllm/README.md`。

## 9. 实测结果

以下都是 2026-10-08 在开发机（Mac，16G 内存，没有独立显卡）上真实跑出来的。

### 9.1 自测

| 脚本 | 内容 | 结果 |
| --- | --- | --- |
| `scripts/kbase_selftest.py` | 入库链路：坏文件拒绝、临时故障重试、重试用完后通知、版本升级 / 冲突 / 回滚、对账修复、邮件发送 | 24 / 24 通过 |
| `scripts/resilience_selftest.py` | 故障注入：知识库 12 项、限流和缓存 4 项、问数 8 项、批量入库 12 项、定时任务和告警 6 项 | 42 / 42 通过 |
| `pytest tests/` | 单元测试 | 126 个通过 |

故障注入自测里观察到的几个数：

- 同样的问题第二次走缓存：约 1.0 秒 → 0.02 秒。
- 批量入库熔断：一批 16 个文件、一半是坏的，处理到第 10 个时失败 5 个（50%），整批自动暂停并推送飞书。
- 重排排不上队时跳过精排仍能作答；但没有精排把关时检索质量会下降，所以降级时改为取前 8 条，答不上来就如实说没找到。

### 9.2 压测

`scripts/loadtest.py`，每个虚拟用户用自己的账号，直接打接口（不是流式）。

| 场景 | 请求数 | 成功 | 被过载保护拒绝（429） | 出错 | 成功请求 P50 | P95 | 命中缓存 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 问数，20 人同时各问 3 题 | 60 | 48 | 12 | 0 | 1.4 秒 | 5.8 秒 | 28 |
| 知识库，20 人同时各问 3 题（七成参数题） | 60 | 24 | 36 | 0 | 1.6 秒 | 13.3 秒 | 2 |
| 知识库，6 人同时各问 4 题 | 24 | 24 | 0 | 0 | 0.3 秒 | 12.6 秒 | 15 |

怎么看这些数：

- **没有一个请求报错或卡死**，这是这一轮改造要保证的。超出并发上限的请求立刻收到「人多请稍后」，而不是排到超时。
- 知识库 20 人同时提问时有六成被拒绝，是因为并发上限设的是 8，而这台机器上重排一次只能跑一个。**这反映的是开发机的算力，不是方案的上限**；上限该设多少，要在 GPU 服务器上压测后再定。
- 压测的题库很小（几十个问题轮着问），缓存命中偏高，P50 因此偏乐观。真实使用时问题更分散。

### 9.3 一次真实的故障

截图时手动停掉了 Milvus 容器再提问：问答没有中断，自动改用关键词检索并在回答上方标出「已降级」，Langfuse 的链路里检索那一步被标成了警告。见 `RAG-03-使用说明书.md` 第五节的截图。

这次真实故障还暴露了一个自测没测出来的问题：**Milvus 容器重启之后，服务里缓存的旧连接是「已关闭」状态，不会自己恢复，问答会一直停在降级状态**（之前评测中途电脑休眠后大量报错也是这个原因）。已修正：检索失败或健康检查失败时丢掉旧连接重新连。修正后重新验证：重启 Milvus 容器期间提问走降级，容器恢复后下一次提问自动回到正常路径，不需要重启服务。

教训是：自测里「把函数换成会抛错的版本」测不出连接状态这类问题，真实地停一次容器才能发现。其他依赖（Redis、RabbitMQ、Neo4j、大模型）用的客户端都会自动重连或每次新建连接，但**没有逐个做过真实的停机验证**。
