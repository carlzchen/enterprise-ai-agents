## 1. 做了什么

按技术架构文档实现了问数 Copilot：ERP 后端（Java）不动，在 `assistant/app/copilot/` 里用 Python 新增一个服务，前端加了三个页面。

| 项 | 数量 |
|---|---|
| 需求文档里的 User Story | 36 条：28 条已实现，2 条是原有功能，3 条部分实现，3 条未实现 |
| 口径库指标 | 41 个（26 个原子指标、15 个派生指标） |
| 白名单视图 | 20 个 |
| 分析模板 | 24 个 |
| 模型可选的工具 | 8 个 |
| 示例制度文档 | 10 份 |
| 单元测试 | 87 个（加上原有 7 个共 94 个，全部通过） |
| 评测集 | 348 题 |
| 新增代码 | Python 约 4,300 行（其中评测和性能对照脚本约 900 行），YAML 约 1,500 行，前端约 700 行，另有 300 行单元测试 |

### 怎么跑起来

```bash
# ERP（MySQL、后端、前端）和助手的基础设施（Milvus、Redis、MongoDB、MinIO）要先启动
cd assistant
docker compose -f ../docker-compose.yml exec -T mysql mysql -uroot -proot < mysql-init/02_copilot.sql
docker compose -f ../docker-compose.yml exec -T mysql mysql -uroot -proot < mysql-init/03_employee_pii.sql
uv run python main.py          # 8090 技术助手、8091 知识库导入、8093 Copilot
```

打开 http://localhost:5180 ，用演示账号登录，左侧菜单"智能问数"。不同角色看到的示例问题和数据范围不一样，建议分别用 `hr01`、`gm`、`prod01`、`sales01` 试一遍。

## 2. 一次提问在代码里怎么走

整个流程是 `pipeline.py` 最下面的 `_pipeline` 函数，普通的 if 和 while，没有用流程框架（最初用了 LangGraph，后来去掉，原因见架构文档第 16 节）。

以 HR 问"上个月伺服线的加班率是多少？"，再追问"那步进线呢？"为例。

| 步骤 | 发生了什么 | 代码 |
|---|---|---|
| 接入 | 校验 ERP 签发的 JWT，从业务库读出这个账号对应的员工、部门子树和产线 | `copilot_server.py`、`permission.load_user` |
| 读记忆 | 从 Redis 取上一轮的工具调用、最近几轮原文、更早的摘要 | `memory.load` |
| 规则路由 | 关键词判断是不是问制度、换图表、改数据。这句不是 | `router.rule_route` |
| 意图缓存 | 同一角色、同一上下文、同一天问过同一句话就直接复用。第一次问没有 | `memory.route_get` |
| 模型路由 | 把筛选后的模板清单、维度字典、Few-shot 例题发给模型，模型返回 `run_template {T07, 过滤: 产线=L5, 时间: "上个月"}`。参数用 Pydantic 校验 | `router.llm_route`、`schemas.py` |
| 时间解析 | "上个月"由代码换算成 2026-09-01 至 2026-09-30，并截到数据截止日 | `timeparse.py`、`template_engine._clamp` |
| 模板填参 | 把过滤值归一成编码、转成字面量，填进模板 SQL | `template_engine.render` |
| 校验 | 语法解析、只能是查询、表白名单、敏感列、危险函数 | `sqlguard.check` |
| 权限改写 | HR 对考勤表是全部权限，不用改写；强制加 `LIMIT 1000`；用 `LIMIT 0` 试运行 | `sqlguard.rewrite`、`guard` |
| 执行 | 先查 Redis 结果缓存，没有再用 `copilot_ro` 账号执行 | `pipeline.execute_sql`、`db.ro_query` |
| 回答 | 结果只有一行，直接由代码拼成一句话，不调用模型 | `result.one_line` |
| 收尾 | 结果暂存（导出用）、更新记忆、写会话历史、写审计 | `pipeline.finalize` |

追问"那步进线呢？"时，模型返回 `run_template {T07, 过滤: 产线=L4, inherit: true}`，没有时间。代码发现 `inherit` 为真，从上一轮继承"上个月"，其余步骤相同（`router.merge_followup`）。

如果问的是"各产线的加班率"，结果有多行：查询一结束，代码先给出第一句（最高和最低的是谁），再让模型流式补充一两句（`result.headline`）。

## 3. 效果评测

### 3.1 评测集

348 题，由 `eval/dataset.py` 生成。问数类的标准答案由手写 SQL 直接在业务库里算出（人事、考勤、工资、生产查底层表，销售和应收查 ERP 自带的事实视图），不是让模型生成的。

| 意图 | 题数 | 说明 |
|---|---|---|
| 制度问答 | 49 | 标注应命中的制度和回答必须包含的关键内容；其中 2 题制度里没有答案，应回答"没有找到" |
| 人员与编制 | 49 | 在职人数、入离职、离职率、离职原因 |
| 考勤工时 | 55 | 出勤率、加班率、迟到旷工、请假 |
| 薪酬与计件 | 44 | 人工成本、人均工资、计件工资、保底、计件单价 |
| 生产与人效 | 42 | 良品数、良率、OEE、人均产量、单位人工成本 |
| 成本与毛利 | 50 | 收入、毛利率、直接人工成本率、采购价差、归因、测算 |
| 回款与结算 | 27 | 回款、应收余额、逾期 |
| 多轮追问 | 32 | 两到三轮，只评最后一轮 |

按题型：数值题 280、制度题 49、应拒绝 13、不能泄露 3、行数 2、应追问 1。其中预期走 SQL 生成的 17 题，归因和测算 6 题。

### 3.2 三轮结果

| 指标 | 第一轮 | 第二轮 | 第三轮 |
|---|---|---|---|
| 意图识别准确率 | 99.4% | 99.7% | 99.7%（347/348） |
| 文档召回准确率 | 100% | 100% | 100%（49/49） |
| SQL 执行成功率 | 99.6% | 100% | 100%（282/282） |
| 指标口径一致率 | 97.1% | 98.6% | 99.3%（274/276） |
| 结果准确率 | 86.5%（301/348） | 98.3%（342/348） | 99.7%（347/348） |
| 模板命中率 | 94.9% | 94.9% | 95.3%（263/276） |
| 其中 SQL 生成路径的准确率 | 64.7%（11/17） | 82.4%（14/17） | 100%（17/17） |

第三轮唯一没过的一题：销售问"上个月回款金额是多少"，预期是明确拒绝（回款记录只对财务和管理层开放），实际是反问"你想看哪类数据"。没有泄露数据，但回应方式不理想。

指标的定义：

- 意图识别准确率：识别出的意图大类和标注一致；应拒绝的题被拒绝即算对。
- 文档召回准确率：标注的制度出现在检索到的 5 个切片里。
- SQL 执行成功率：SQL 通过校验并执行成功。
- 指标口径一致率：命中了标注的模板（模板 SQL 就是口径库的定义），或者走 SQL 生成且结果和标准 SQL 一致。
- 结果准确率：标准答案的数字出现在结果的目标行里（相对误差千分之二以内）；制度题看回答是否包含全部关键内容；权限题看是否被拒绝、有没有泄露。

### 3.3 Bad Case 分析

第一轮 47 题没过，归成 8 类原因：

| 原因 | 题数 | 例子 | 怎么改的 |
|---|---|---|---|
| 问合计时被自动加了默认分组 | 36 | 问"三季度销售收入多少"，结果按月份分了三行，没有合计 | 模板引擎不再自动套默认分组，用户没要求分组就返回合计；提示词里写明什么时候填分组 |
| 该走 SQL 生成却套了模板 | 3 | "逾期超过 90 天的发票有几张"套了应收模板 | 提示词加规则和例题：带数值门槛、按员工统计的问题走 SQL 生成 |
| 部门认不出 | 2 | "智能驱控车间有多少人"被当成事业部或产线 | 把部门树放进维度字典 |
| 只能看本人数据的人拿到了"部门统计" | 2 | 销售问"各部门人均工资"，系统用他一个人的工资条算了个"部门平均" | 视图被限定成仅本人、问题又不是在问本人时，直接拒绝 |
| 时间短语不认识 | 1 | "2025 年 12 月底" | 时间解析支持"月底、年底" |
| 模板缺指标 | 1 | "实发工资总额"被套进人均工资模板 | 人工成本模板增加实发工资和个税两列 |
| 排序列不对 | 1 | "报废数最多的型号"按良率排了序 | 模板调用增加"按哪个结果列排序"参数 |
| 查本人数据时加了多余条件 | 1 | "我 8 月的工资"生成了 `emp_no = '本人'` | SQL 生成的表结构说明里标注"系统已限定为本人，不要再按姓名过滤" |

第二轮 6 题没过：

| 原因 | 题数 | 怎么改的 |
|---|---|---|
| 评测集标注不合理（系统答对了，但标注的目标行写错） | 3 | 修正标注 |
| 问占比时用了过滤而不是分组 | 1 | 提示词加规则和例题 |
| 漏掉了问题里点名的客户 | 1 | 提示词加规则和例题 |
| "查出来给我"里的"我"被当成在问本人数据 | 1 | 判断前先去掉"给我、帮我"这类说法 |

"SQL 校验不通过就把错误还给模型重写"这个回路，三轮评测里一次都没有触发（模型写的 SQL 都一次通过）。它的正确性是另外单独验证的：故意让第一次生成的 SQL 写错字段名，第二次拿到错误信息后改对，结果正确；一直写错则在重写 2 次后停止并提示用户。

三轮一共处理了 51 个没通过的题，其中 3 个是评测集自己的问题，48 个是系统的问题，归成 11 类原因。

### 3.4 这些数字要怎么理解

- **没有留出集**。评测集是我自己构建的，三轮调试用的也是这一份。99.7% 说明"评测集覆盖到的问法基本都能答对"，不能说明真实用户随便问也有这个准确率。真实使用时准确率会更低，尤其是 SQL 生成路径。
- **评测集的问法比较规整**。题目是按模式批量生成的（同一种问法换月份、换产线），覆盖面有了，但口语化、错别字、一句话问两件事这些情况很少。
- **数据是模拟的**。真实 ERP 的脏数据、口径争议、历史遗留字段都没有。
- **SQL 生成路径只有 17 题**，样本小。
- 要让数字更可信，下一步应该：找几个没参与开发的人每人写 30 个问题当留出集；把线上点踩的问题持续加进评测集。

## 4. 性能

同一批 32 次提问（28 个话题，含多轮追问；模板问数、SQL 生成、制度问答、归因、测算都有）分别用三种方式跑，脚本是 `eval/bench.py`。

| 方式 | 首字响应 P50 | 首字响应 P95 | 平均总耗时 | 平均 Token | 最大 Token | 平均模型调用次数 |
|---|---|---|---|---|---|---|
| 优化前 | 2.67 秒 | 4.58 秒 | 2.91 秒 | 5,791 | 9,521 | 2.09 |
| 优化后，缓存未命中 | 2.22 秒 | 4.42 秒 | 3.59 秒 | 4,338 | 6,463 | 1.84 |
| 优化后，缓存命中 | 0.03 秒 | 2.08 秒 | 0.33 秒 | 321 | 4,126 | 0.12 |

- "优化前"指：不用规则路由，把全部 24 个模板和全部视图结构都发给模型，不用任何缓存，不做流式（等回答全部生成完才返回，所以首字时间等于总耗时）。
- "首字响应"指从收到问题到第一段回答文字推给用户的时间。

### 做了哪些优化

| 手段 | 做法 | 效果 |
|---|---|---|
| 规则路由 | 问制度、换图表、要求改数据，用关键词直接分流 | 省掉一次模型调用。评测集 348 题里有 38 题走规则 |
| 模板筛选 | 模板清单先按角色过滤，再用检索挑出最相关的 8 个发给模型 | 和 Schema 裁剪一起，平均 Token 从 5,791 降到 4,338（降 25%） |
| Schema 裁剪 | SQL 生成时只给最相关的 4 个视图，并去掉这个角色看不到的列 | SQL 生成类问题的 Token 从约 9,500 降到约 6,400 |
| 单行结果不调模型 | 结果只有一行时，由代码把数字拼成一句话 | 省掉一次模型调用 |
| 首句直出 | 多行结果的第一句（最高、最低或最新一期）由代码生成，查询一结束就推送，模型只补充 | 首字不用等第二次模型调用 |
| 流式输出 | 进度、表格、图表、文字依次推送 | 用户不用盯着空白等 |
| 三层缓存 | 意图识别结果、查询结果、回答文字各缓存 10 分钟；键里带角色和行级范围 | 命中时不调用模型，首字 P50 降到 0.03 秒 |
| 上下文压缩 | 超过 4 轮的历史压成摘要，在后台做 | 这批问题最多 3 轮，没有体现出来 |

### 怎么看这组数字

- **缓存没命中时，首字时间的改善有限**（P50 降了 17%，P95 基本持平）。时间主要花在意图识别那一次模型调用上，大约 1.2 到 2 秒，这一步目前省不掉。SQL 生成类问题要连续调两次模型才有结果，是 P95 的主要来源。
- **明显的收益在 Token 和缓存命中后**。看板"问一问"、常见问题这类重复提问，命中缓存后几乎是即时返回。
- **模型接口的耗时波动很大**。同一个脚本前一次运行，"优化前"的 P50 是 3.01 秒、P95 是 6.82 秒；这次是 2.67 秒和 4.58 秒。样本只有 32 次，P95 由最慢的一两次决定，不要把它当成稳定值。
- 缓存命中那一行里 P95 仍有 2.08 秒，是因为 SQL 生成类问题和个别追问没有命中意图缓存。

## 5. 压测

用 JMeter 对 `POST /chat` 做并发压测，计划文件是 `assistant/loadtest/copilot_query.jmx`。分两组：

| 组 | 并发 | 请求数 | 错误 | 平均 | P50 | P95 | P99 | 吞吐 |
|---|---|---|---|---|---|---|---|---|
| 高频问题（12 个问题循环，意图和结果缓存都命中，不生成文字回答） | 50 线程 | 1,000 | 0 | 624 ms | 679 ms | 918 ms | 1,097 ms | 58.2 次/秒 |
| 不重复的问题（60 个问题里取 30 个，每次都要调用模型，关闭缓存） | 5 线程 | 30 | 0 | 1,929 ms | 1,664 ms | 3,548 ms | 4,242 ms | 2.3 次/秒 |

- 第一组测的是系统自身：鉴权、读记忆、SQL 校验和改写、读缓存、写会话历史和审计。压测前先把 12 个问题各问了一遍做预热。
- 第二组测的是带模型的完整链路，瓶颈在模型接口，所以只开了 5 个并发。
- 服务是单进程。50 并发下单次请求从空闲时的约 30 毫秒涨到 600 多毫秒，说明这时已经排队了；要更高的吞吐需要开多个进程。
- 这是在一台笔记本上、所有组件都在本机时测的，只能说明量级。
- 压测用专门的账号签发令牌（`scripts/mint_token.py loadtest ADMIN`），这样压测产生的会话和审计记录都在 `loadtest` 名下，不会混进真实用户的记录。这次压测结束后已经把这些记录清掉了。

下面每一条都实际跑过（单元测试或真实请求）。

| 场景 | 结果 |
|---|---|

| 研发问"我 8 月的应发工资" | 只返回本人的一行 |
| 研发问"全公司 8 月人工成本" | 拒绝：模板不对这个角色开放 |
| 销售问"各部门人均工资" | 拒绝：只能看本人工资条，不能看部门统计 |
| 管理层查员工身份证号、手机号 | 能查，全部打码，如 `3601**********0099` |
| 人力资源查同样的内容 | 明文 |
| 财务查工资卡号 | 明文（发工资要用），身份证和手机号仍然打码 |
| 销售要别人的身份证号 | 拒绝 |
| "把所有员工的工资改成一万" | 规则直接拒绝，不调用模型 |
| SQL 里写 `DELETE`、`DROP`、多条语句、`SLEEP`、`@@version`、系统库 | 全部在校验阶段拒绝 |
| 查白名单以外的表（如 `hr_employee`） | 校验阶段拒绝；即使绕过，`copilot_ro` 账号在数据库里也没有这张表的权限 |
| 在 SQL 末尾加 `OR 1 = 1` 想绕过行级限制 | 无效，行级条件加在内层子查询 |
| 导出别人查出来的结果 | 拒绝 |
| 没点确认就下载导出文件 | 404，文件还没有生成 |
| 普通用户看审计日志 | 拒绝，仅管理员 |

## 7. 没做的和已知的不足

| 项 | 说明 |
|---|---|
| 阈值预警订阅（US-404） | 没做。需要定时任务和通知渠道 |
| Excel 台账解析（US-503） | 没做 |
| 制度加个人数据的混合问答（US-103） | 没做。ERP 里也没有年假余额这类数据 |
| PDF 制度导入 | 没做。只支持 Markdown、纯文本、Word |
| 自动多层下钻（US-402） | 只能靠追问一层层换分组 |
| Bad Case 自动进评测集（US-1002） | 点踩会进 Bad Case 池并可标注原因，但加入评测集要人工写标准 SQL |
| 行级权限的粒度 | 按部门子树或"仅本人"。演示账号里生产总监的范围覆盖全部产线，没有车间主任账号，所以"只看一条产线"只在单元测试里验证过 |
| 意图缓存可能过期 | 缓存 10 分钟。这期间如果模板或口径改了，要等缓存过期或重启 |
| 导出状态存在内存里 | 等待确认的导出请求保留 30 分钟；服务重启后会丢失，需要重新发起 |
| Copilot 服务没有容器化 | 和技术助手一样跑在宿主机上，重启后要手动拉起 |
| 没有留出评测集 | 见 3.4 |
| 模型依赖 | 意图识别和 SQL 生成都依赖 DeepSeek，换模型后需要重新评测 |
